# KAN JOB HUNTER

Автономный локальный монитор публичных Telegram-источников с вакансиями и заказами для фотографа, видеографа, оператора, видеомонтажёра и преподавателя видеосъёмки/монтажа/цветокоррекции.

AI-креаторы и motion-дизайнеры исключаются эвристическим фильтром.

## Установка

```bash
cd /Users/a8/Documents/GitHub/capcut-desktop-editing/KAN_JOB_HUNTER
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env`:

- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — пользовательский Telegram API;
- `BOT_TOKEN` — токен отдельного бота для уведомлений;
- `NOTIFICATION_CHAT_ID` — ваш чат с ботом или разрешённый рабочий чат.

Секреты не печатаются и не записываются в логи.

## Запуск

```bash
.venv/bin/python -m kan_job_hunter init
.venv/bin/python -m kan_job_hunter auth
.venv/bin/python -m kan_job_hunter discover
.venv/bin/python -m kan_job_hunter check
./start.sh
```

`auth` использует локальный терминал Telethon. Код и пароль не вводятся в чат Codex.

## Что реально делает MVP

- Ищет публичные каналы и группы через `contacts.SearchRequest` по русским и англоязычным запросам.
- Анализирует последние сообщения найденных источников.
- Сохраняет только публичные источники с username; автоматически вступать не пытается.
- Дедуплицирует источники и сообщения в SQLite.
- Проверяет сохранённые источники по расписанию.
- Отправляет новые релевантные объявления через Telegram-бота с кнопками «Открыть», «Подготовить отклик», «Сохранить», «Неинтересно».
- Сохраняет оригинальную ссылку, дату, оплату и контакт только если они реально указаны в сообщении.
- Повторный запуск безопасен: сообщения с той же парой `source_id + telegram_message_id` не уведомляются повторно.

## Ограничения текущего этапа

- Для пользовательского поиска и чтения источников нужна авторизованная Telethon-сессия.
- Доступность истории зависит от прав Telegram и публичности источника; вступление не выполняется.
- «Подготовить отклик», «Сохранить» и «Неинтересно» пока создают кнопки, но обработчики действий будут добавлены следующим этапом.
- Событийная обработка новых сообщений подключается после подтверждения источников и прав доступа; текущий MVP использует безопасный polling.
- Оценка соответствия основана на прозрачных ключевых словах, без внешней AI-модели и без выдумывания отсутствующих данных.
- Лимиты Telegram соблюдаются через последовательные запросы и обработку исключений; платные API не используются.

## GitHub Actions: локальная подготовка

Проект содержит локально подготовленный workflow в корне репозитория:

`.github/workflows/kan-job-hunter.yml`

Workflow работает из публичного репозитория, но state-файл хранит только в отдельном приватном репозитории и запускает:

- обычную проверку каждые 30 минут (`17` и `47` минут часа);
- ежедневный `discover` в 03:07 UTC;
- ручной запуск через `workflow_dispatch`;
- только один экземпляр одновременно через `concurrency`;
- ограничение выполнения пятью минутами.

Для GitHub Actions интерактивная авторизация не используется. После локальной QR-авторизации выполните:

```bash
.venv/bin/python -m kan_job_hunter export-session
```

Команда записывает StringSession только в игнорируемый файл:

`data/telegram_session_string.txt`

Сам StringSession никогда не печатается. Содержимое файла нужно вручную добавить в GitHub Settings → Secrets and variables → Actions → New repository secret под именем `TELEGRAM_SESSION_STRING`, затем локальный файл можно удалить.

Добавьте семь Repository Secrets:

```text
TELEGRAM_API_ID
TELEGRAM_API_HASH
TELEGRAM_SESSION_STRING
BOT_TOKEN
NOTIFICATION_CHAT_ID
STATE_REPO
STATE_REPO_TOKEN
```

SQLite не коммитится в публичный репозиторий и не загружается в его artifacts. Workflow клонирует отдельный приватный state-репозиторий из `STATE_REPO`, восстанавливает `kan_job_hunter.sqlite3`, а после проверки коммитит обновлённую базу обратно туда. `STATE_REPO_TOKEN` должен иметь только `Contents: Read and write` для этого приватного репозитория.

Публичный репозиторий не получает `contents: write` и `actions: write`; workflow использует только `contents: read`. Секреты, `.session`-файлы, `.env` и SQLite не входят в публичные artifacts или коммиты. Не добавляйте `pull_request`/`pull_request_target` к этому workflow.

Ожидаемый минимальный расход для приватного GitHub Free — около 1440 runner-минут в 30-дневном месяце, если каждый запуск округляется до одной минуты: 48 запусков в сутки × 30 дней. Установка Python-зависимостей и сетевые задержки могут увеличить длительность job, поэтому после первого ручного запуска нужно проверить фактическое использование минут. Расписание 5 или 15 минут для лимита 2000 минут не подходит.
